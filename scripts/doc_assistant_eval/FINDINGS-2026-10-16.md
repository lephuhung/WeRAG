## 2. abbr_typo — verdict: test bug (the gate's intended behaviour is auto-correct)

**Evidence.** Step 0 event: `abbreviation_resolution {"status":"ready","auto_corrections":[{"wrong":"cascc","correct":"các"}],"unknown_terms":[],"terms":[]}`. Step 2: `auto_corrections:[{phaps→pháp}]`, `terms:[{short_form:"bhxh", full_form:"Bảo hiểm xã hội", source:"dictionary_active"}]`; log `abbreviation gate: suspects=1 corrected=1 asked=0`, effective query `pháp luật về Bảo hiểm xã hội (bhxh) cho cán bộ ubnd xã …`. Steps 1 and 3 SKIP because `_pick_typo` derives the resend from a card that no longer appears.

**Code confirms auto-correct is intended.** `internal/vietnamese_legal/abbreviation/evidence.go:62 DecideTypo`: with `!e.Ask`, any reading with ≥2 votes (spellcheck, chat rewrite, Telex decoder, dictionary near-form, memory) → `TypoCorrect`; `fuseTypos` (`internal/application/service/abbreviation_turn.go` ~line 480) turns that into `corrections` → `AutoCorrections` on the resolution (`internal/types/abbreviation_resolution.go:179`). The card appears only for `TypoAsk` (sources disagree) or when the client sends `recheck_words` (`internal/handler/session/types.go:75` → `AbbreviationAskWords` → `e.Ask` → always `TypoAsk` with the readings as options).

**Observable signals of a silent correction:**
- `abbreviation_resolution` event with `status == "ready"` and `auto_corrections` containing `{wrong, correct}`; no `abbreviation_choice` display type.
- UI: `frontend-next/components/chat-client.tsx:493` renders the corrected words with the **"Không phải?"** button (`chat.typoReject`), whose handler `rejectReading` (~line 2707) resends the same query with `recheck_words: [wrong…]`.

**Scenario rewrite** (`scenarios.py`; add `extra: Optional[Dict[str, Any]] = None` to `Step` and pass `extra=step.extra` to `client.chat` in `run_eval.py` — `WeragClient.chat` already merges `extra` into the body):

```python
def _auto_corrected(word, guess):
    def fn(t, ctx):
        for st in _abbr_states(t):
            for c in st.get("auto_corrections") or []:
                if str(c.get("wrong", "")).lower() == word:
                    return st.get("status") == "ready" and str(c.get("correct", "")).lower() == guess, f"auto_corrections {st.get('auto_corrections')}"
        return False, "no auto_correction"
    return C.custom(f"'{word}' silently read as '{guess}' (undo via 'Không phải?')", fn)

steps=[
  Step("số lượng hồ sơ cascc loại ưu tiên là bao nhiêu",
       S(_auto_corrected("cascc", "các"), C.no_display_type("abbreviation_choice"),
         C.answer_not_contains(["chưa rõ ý nghĩa", "nghĩa đầy đủ"]), C.no_edit_ops()),
       note="Hai nguồn đồng ý 'các' → tự sửa; UI hiện nút 'Không phải?'."),
  Step("số lượng hồ sơ cascc loại ưu tiên là bao nhiêu",          # simulate 'Không phải?'
       S(_unclear_card("cascc", "các"), C.answer_contains_any(["chưa rõ ý nghĩa"]), C.no_edit_ops()),
       extra={"recheck_words": ["cascc"]}),
  Step(_pick_typo("cascc"), S(_typo_fixed("cascc"), C.no_display_type("abbreviation_choice"), C.no_edit_ops())),
  Step("phaps luật về bhxh cho cán bộ ubnd xã quy định gì",
       S(_auto_corrected("phaps", "pháp"), _abbr_looked_up("bhxh"),
         C.custom("ubnd looked up", lambda t, ctx: "ubnd" in {str(x.get("short_form","")).lower() for st in _abbr_states(t) for x in st.get("terms") or []}, status=WARN),
         C.no_display_type("abbreviation_choice"), C.no_edit_ops())),
]
```

**Side finding.** In step 2 `ubnd` was *not* resolved (`candidate_count=1`, terms only `bhxh`) although the dev dictionary has UBND, so `_abbr_looked_up("ubnd", …)` would fail. Keep it WARN and investigate separately: lower-case `ubnd` is probably dropped by the detector or `SettledWithoutAsking` (`abbreviation/settled.go:75`, `IsCommonAbbreviation`) before the dictionary lookup.

**Verify.** `--only abbr_typo`: step 1 PASS via auto_corrections, step 2 shows the card, steps 3–4 run (no SKIP).

## 5. abbr_choice step 2 — verdict: agent bug (no per-tool call cap) + judge truncation

**Evidence.** 23 tool calls in one turn: 2 × search_knowledge then **21 × search_document_section** on knowledge 8cc1c936 (Luật ATTP 55/2010): Điều 28, 29, 30, 11, 12, 13, 10, 14 … 27, one per round, 87.8 s. Judge: "bị ngắt quãng ở cuối ('Dụng cụ, đồ chứa đ')". The answer is 7128 chars and that string is at offset **5982**; `judge.py` passes `turn.text[:6000]`. The real answer ends "…xác định các điều khoản còn hiệu lực." — complete. Not a stream/max_tokens cut.

**Root cause of the loop.** `internal/agent/turn_guards.go` only caps *failed* calls (`maxToolFailuresPerTurn = 3`). Successful calls of one tool are unlimited up to `max_iterations: 30`; `search_document_section` says "One section per call", so the model enumerates articles one by one.

**Fix.** In `turn_guards.go` add a per-turn cap on calls of the same tool regardless of success, for read tools:

```go
var maxToolCallsPerTurn = map[string]int{
    ToolSearchDocumentSection: 6, "read_document": 6, "read_document_outline": 6, "search_knowledge": 6,
}
const toolCapNote = "\n\n[Đã gọi %s %d lần trong lượt này; công cụ không còn được cung cấp nữa. " +
    "Trả lời người dùng với những gì đã có; nếu cần đọc thêm, dùng read_document(id=…) theo trang thay vì từng Điều.]"
```
`toolCallCounts(steps)` counts all calls; `dropExhaustedTools` also drops tools at/over their cap; `noteExhaustedTools` appends `toolCapNote` to the **Output** of the call that reaches the cap. GitNexus impact of both: LOW (callers `engine.go:601`, `engine.go:960`). Cheaper for the model as well: let `search_document_section` accept `sections: [...]` (≤10) in one call (`internal/agent/tools/search_document_section.go` schema + loop; output grouped per section).

**Judge fix:** §9.

**Verify.** `--only abbr_choice` 3×: ≤8 tool calls per turn, turn < 40 s, no truncation FAIL. Unit test for `dropExhaustedTools` with 6 successful calls.

## 6. multi_source_readonly — verdict: small agent bug + model nondeterminism

**Evidence.**
- First run: only `read_document_outline(vb2)`; the model wrote a rewrite in chat and said "tự chỉnh sửa trong văn bản" — never said the source is read-only (check needs one of `tài liệu nguồn|chỉ tra cứu|không sửa|không thể sửa|mở`).
- OO rerun: `rewrite_paragraphs({"edits":[…],"mode":"propose"})` **without `document`** → `errRewriteNeedsSelection` ("chưa bôi đen đoạn nào…"), and the answer told the user to *highlight the passage in ke_hoach_nguon.docx*, which is impossible (a source has no editor). PASS only because "mở" appeared.
- Add-in rerun: no edit tool; answer contained "tài liệu nguồn chỉ mang tính tham khảo" → PASS.

**Root cause.** `resolveDocument` (`internal/agent/tools/document_workspace.go:121`; GitNexus impact MEDIUM — 7 direct callers, all document tools) with `forEdit && ref == ""` narrows `docs` to targets **before** looking at the turn's @-mentions (line 162, only within `docs`). With one target and one mentioned source it silently picks the target; `SourceDocumentRefusal` (line 43: "vbN là tài liệu nguồn, chỉ tra cứu được; mở nó để soạn thảo nếu cần sửa.") is never reached.

**Fixes.**
1. `resolveDocument`: at the top of the `forEdit && ref == ""` branch, before narrowing: if `types.MentionedDocumentsFromContext(ctx)` has exactly one id and that document `IsSource()` → `return nil, errors.New(SourceDocumentRefusal(d))`. Read tools unaffected (`forEdit=false`). Test in `document_workspace_test.go`.
2. Code-generated note for the no-tool case (prompt rules are ignored by Qwen): mirror `appendLegalHistory`/`appendWikiCaveat` in `finalize.go` with `appendSourceEditNote`: when the turn's mentions resolve **only to sources**, the query matches `viết lại|sửa|chèn|bổ sung|thay|cập nhật`, and no edit tool succeeded, append one fixed line: "Lưu ý: ke_hoach_nguon.docx là tài liệu nguồn (chỉ tra cứu); đề xuất trên chỉ hiển thị trong chat — mở tệp trong trình soạn thảo nếu muốn áp dụng." The scenario's phrase check then passes deterministically.

**Verify.** `--only multi_source_readonly` 3×: any `rewrite_paragraphs` error is `SourceDocumentRefusal`; answer always contains "tài liệu nguồn".
